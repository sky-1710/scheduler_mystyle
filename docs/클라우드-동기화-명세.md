# 클라우드 동기화 명세서 (미구현 — 향후 계획)

> 상태: **설계만 완료, 구현 안 됨.**
> 목적: 태블릿·휴대폰까지 데이터가 자동 연동되도록 할 때, 이 문서만 보고 바로 구현할 수 있게 결정사항과 설계를 기록해둔다.

---

## 1. 목표

- PC / 태블릿 / 휴대폰 어디서든 **같은 계정으로 로그인하면 몇 초 안에 같은 데이터**가 보인다.
- 지금의 **로컬 우선(local-first) 구조는 유지**한다 — 오프라인에서도 완전히 동작하고, 클라우드는 "동기화 거울" 역할만 한다.
- 개인정보: 데이터는 **사용자 본인 소유의 무료 클라우드 프로젝트**에만 저장되고, 본인만 읽을 수 있다.

## 2. 기술 선택: **Supabase** (Firebase 대신)

| 비교 항목 | Supabase | Firebase |
|---|---|---|
| DB 무료 한도 | 500MB (Postgres) | Firestore 1GiB |
| **파일 저장(사진)** | **무료 1GB 포함** | Storage는 유료 플랜(Blaze) 필요 (신규 프로젝트 기준) |
| 문서 크기 제한 | 넉넉함 (jsonb) | 문서당 1MiB — 사진 포함 JSON이 초과할 수 있음 |
| 구글 로그인 | 지원 | 지원 |
| 실시간 갱신 | Realtime 구독 지원 | 지원 |

**결정: Supabase.** 사진(dayImages)까지 무료로 커버되고, 데이터 전체를 jsonb 한 컬럼에 넣는 단순한 설계가 가능하다.

## 4. 서버 스키마 (Supabase SQL Editor에 그대로 실행)

```sql
-- 사용자당 1행: 플래너 전체 데이터(사진 제외)를 jsonb로 보관
create table planner_data (
  user_id uuid primary key references auth.users(id) on delete cascade,
  data jsonb not null,
  updated_at timestamptz not null default now(),
  device text  -- 마지막으로 쓴 기기 이름 (디버그용)
);

alter table planner_data enable row level security;

create policy "본인 데이터만 읽기" on planner_data
  for select using (auth.uid() = user_id);
create policy "본인 데이터만 쓰기" on planner_data
  for insert with check (auth.uid() = user_id);
create policy "본인 데이터만 수정" on planner_data
  for update using (auth.uid() = user_id);
```

사진(Storage): 버킷 `photos` 생성(비공개), 정책은 경로 첫 폴더 = 본인 uid 일 때만 읽기/쓰기 허용.
경로 규칙: `photos/{user_id}/{YYYY-MM-DD}/{index}.jpg` (dataURL 대신 jpg 바이너리로 업로드).

## 5. 데이터 모델 매핑

- `data` jsonb = 현재 `schedule_data.json` v3 페이로드에서 **dayImages를 제외한 전부**
  (events, blocks, blockMin, blockOff, blockExtra, timeLog, dayTasks, dayGoals, dayMemos, dayBad, dayRatings, sleepLog, habits, habitChecks, todoDone, categories)
- `dayImages`는 Storage에 개별 파일로. 로컬에는 지금처럼 IndexedDB 캐시 유지.
- 클라이언트에 새 메타 저장: `localStorage.cloud_lastSyncedAt` (마지막으로 서버와 일치했던 updated_at).

## 6. 동기화 알고리즘

### 기본 원칙: Last-Write-Wins(LWW) + 덮어쓰기 전 안전 백업

v1은 블롭 단위 LWW로 단순하게 간다. 두 기기를 **동시에 오프라인 편집**하는 경우만 충돌이 나며, 이때 지는 쪽 데이터는 자동 백업으로 보존한다.

```
[앱 시작 / 온라인 복귀 / Realtime 알림 수신 시] pullCloud():
  remote = select data, updated_at from planner_data where user_id = me
  if remote 없음:
      pushCloud()  # 첫 기기 → 서버에 씨딩
  elif remote.updated_at == cloud_lastSyncedAt:
      # 서버가 그대로 → 내 로컬 변경만 있으면 push
      if 로컬변경있음: pushCloud()
  elif 로컬변경없음 (마지막 push 이후 저장 이벤트 없음):
      로컬 ← remote 적용, render(), cloud_lastSyncedAt = remote.updated_at
  else:
      # 충돌: 서버도 나도 바뀜
      현재 로컬 상태를 data 폴더/다운로드로 "conflict_백업_시각.json" 저장
      로컬 ← remote 적용 (서버 우선)   # v1 정책
      toast("다른 기기 변경을 적용했습니다. 이전 상태는 백업됨")

[saveEvents() 끝에] queuePush():
  debounce 3초 → pushCloud()

pushCloud():
  upsert planner_data set data=현재상태(사진 제외), updated_at=now(), device=기기명
  cloud_lastSyncedAt = 방금 updated_at
```

- **Realtime**: `planner_data` 행 변경 구독 → 다른 기기가 push하면 이 기기에서 pullCloud() 실행. (탭 간 동기화용 기존 `storage` 이벤트 리스너와 같은 패턴)
- **로컬변경있음 판정**: `saveEvents()`가 `cloud_dirty=1` 플래그를 세우고 push 성공 시 해제.
- v2(선택): 날짜 키 단위 병합 — blocks/timeLog/habitChecks 등은 `{날짜: …}` 구조라, 날짜별로 최근 수정 시각을 기록하면 필드 수준 병합이 가능하다. v1에서 충돌 빈도를 보고 결정.

### 사진 동기화 (2단계로 분리 가능)

- push: IndexedDB의 dayImages 중 서버에 없는 파일 업로드 (경로로 존재 확인)
- pull: 서버 목록과 로컬 비교 → 없는 것 다운로드해 IndexedDB에 저장
- 삭제: 로컬에서 삭제 시 Storage에서도 삭제
- v1에서 생략해도 됨 — 그 경우 사진만 기기별 보관임을 설정 화면에 명시

## 8. 개인정보·보안 메모

- anon key는 공개되어도 되는 값이다 — 실제 접근 제어는 RLS(행 수준 보안)가 담당하며, 위 정책상 **본인 uid의 행만** 읽고 쓸 수 있다.
- 데이터 소유권: Supabase 프로젝트 자체가 사용자 계정 소유. 앱 제작자를 포함해 제3자가 볼 수 없다.
- 앱 코드만 공개될 뿐(호스팅), 데이터는 코드 저장소에 절대 포함하지 않는다 (3절 .gitignore).
- 완전한 비밀이 필요하면 v3에서 클라이언트 측 암호화(비밀구절로 AES 암호화 후 업로드)를 검토.

| 항목 | 예상 | 무료 한도 |
|---|---|---|
| DB 용량 | 수 MB (텍스트 데이터) | 500MB |

## 10. 테스트 시나리오 (구현 후 반드시 확인)

1. 기기 A 로그인 → 데이터 씨딩 → 기기 B 로그인 → A의 데이터가 그대로 보임
2. A에서 할일 추가 → 3초 내 B 화면에 자동 반영 (Realtime)
3. B를 오프라인으로 → A에서 수정 → B 온라인 복귀 → B에 반영
4. **충돌**: A·B 모두 오프라인에서 서로 다른 수정 → 둘 다 온라인 → 늦게 push한 쪽 기준으로 통일되되, 진 쪽 백업 파일 생성 확인
5. 로그아웃 상태에서는 지금과 100% 동일하게 동작 (회귀 없음)
6. 사진 추가 → 다른 기기에서 표시 (2단계 구현 시)
